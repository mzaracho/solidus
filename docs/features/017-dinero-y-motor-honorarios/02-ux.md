# 017 — UX/UI: edición de monto y pagador, pagador con reglas y baja de staff

Fecha: 2026-11-18. Idioma de la interfaz: español rioplatense (voseo), como el resto de la app.
Alcance: solo lo que exige la spec (#45, #75, #76). No se rediseña la pantalla de reglas de honorarios.

## 0. Hallazgos del frontend actual (base del diseño)

1. **Formularios que editan una atención** (los únicos que pueden tocar monto o pagador):
   - `workload/RetroactiveModal.tsx` (usado desde `workload/columns.tsx`, acción "Editar").
   - `workload/form/WorkItemForm.tsx` con `initialData` (usado por `pro/atenciones/AtencionesTable.tsx` y
     `org/admisiones/AdmisionesTable.tsx`, ambos llaman `updateWorkItem(orgSlug, id, data)`).
   - Las acciones rápidas (`updateWorkItem(..., { paymentStatus })`, `{ attendance }`, `DeudoresTable`) no tocan monto
     ni pagador: no cambian.
2. **`RetroactiveModal` hoy** tiene cuatro problemas que esta feature toca:
   - el select de pagador tiene **opciones fijas** (OSDE, Swiss Medical, Particular) y manda el **nombre**, no un id;
   - el candado es por **antigüedad (> 30 días)** y no por "cobrada" (regla solo de frontend, el backend no la tiene);
   - muestra un **"Nuevo Neto Estimado ... (70%)"** inventado (`amount * 0.7`), que es falso: con la nueva regla el
     backend recalcula con las reglas reales;
   - `handleSave` cierra el modal **antes** de saber si el backend aceptó, y `columns.tsx` avisa éxito aun cuando el
     backend ignoraba el cambio (origen de #45).
3. **`WorkItemForm` en edición**:
   - el monto se habilita/deshabilita solo por reglas de preset (`enforceOrgRules && (presetId || baseValue)`);
   - el efecto de "precio del preset" (líneas ~253-279) **recalcula `gross` al abrir** una atención existente con
     preset: puede mandar un monto distinto del guardado sin que el usuario lo toque;
   - en modo profesional el pagador se inicializa con `initialData.payerId || ''`, pero `isPrivate` arranca en
     `true`: una atención sin pagador termina enviando `payerId: ''` (valor falso) o se interpreta como "Particular";
   - el select de pagador solo se muestra si no es "Paciente Particular".
4. **Pagador faltante**: `data-schema.ts` convierte nombre nulo o `'Unknown'` en `'—'` (`payerName: '—'`), y ese `'—'`
   viaja de vuelta como valor desde el modal (M2 del 008).
5. **`ACTIVITY_UPDATE_FIELDS`** (`request-bodies.ts`) hoy no incluye `grossAmount` ni `payerId`.
6. **Pagadores**: no existe UI ni función `deletePayer` en el frontend. `PayerRulesManager.tsx` (Configuración > Fees) solo
   lista, crea y edita el porcentaje (cada edición confirmada crea una fee rule vía `createFeeRule`). Esa pantalla ya
   carga `getFeeRules()`, así que **sabe qué pagadores tienen regla** (`rules.find(r => r.payerId === p.id)`).
7. **Staff**: `org/profesionales/page.tsx` ya usa `ConfirmDialog` ("Eliminar a {nombre}" / "¿Estás seguro de que deseas
   eliminar este profesional? Esta acción no se puede deshacer.") y toast "Profesional eliminado". Errores por
   `errorMessageOf`.
8. **`errorMessageOf` / `toApiError`** devuelven el `errors[0].message` del backend en los 4xx (excepto 404 y
   `validation-failed`, que usan texto genérico). Por eso el texto de un 409 de negocio **lo pone el backend**; el front
   no necesita mapear por `code` salvo para decisiones de comportamiento (refrescar, bloquear). Las claves de la
   sección 7 son el respaldo y la fuente de textos de UI propios.
9. **`ConfirmDialog`** (`ui/confirm-dialog.tsx`) se cierra solo apenas se confirma (`onConfirm(); onClose()`): no
   muestra estado de carga ni deja abierto ante un error. Sirve para borrados simples; no para edición.

## 1. Flujo del usuario

### A. Corregir monto o pagador de una atención no cobrada
1. El usuario abre "Editar" en una atención (tabla de Atenciones, Admisiones o Prestaciones).
2. Ve monto y pagador habilitados (y la leyenda de ayuda corta bajo el monto, ver 2.1).
3. Cambia monto, pagador o ambos. En cuanto el valor difiere del guardado aparece el **aviso de recálculo** y el botón
   principal pasa a "Guardar y recalcular".
4. Pulsa el botón: queda en estado "Guardando…" (deshabilitado, con spinner), el diálogo sigue abierto.
5. Éxito: el diálogo se cierra, toast "Atención actualizada. Se recalcularon los honorarios." (si cambió monto/pagador)
   o "Atención actualizada." (si no), se refrescan los datos (`router.refresh()` o la recarga propia de la tabla) y el
   foco vuelve al botón "Editar"/fila que abrió el diálogo.
6. Error: el diálogo sigue abierto, con el mensaje (ver 4) y el foco en el aviso de error.

### B. Atención cobrada
1. El usuario abre "Editar". Monto y pagador se ven bloqueados con el texto explicativo (2.2).
2. Puede editar el resto de los campos (fecha, asistencia, medio de pago, etc.). No hay aviso de recálculo.
3. Guardar manda solo los campos modificados; nunca monto ni pagador.

### C. La atención se cobró mientras se editaba
Ver sección 4.

### D. Borrar un pagador (si se agrega el botón, ver 5) y borrar un profesional
Ver secciones 5 y 6.

## 2. Edición de atención

### Reglas comunes para los dos formularios
- **"Cobrada"** = la misma definición que la salvaguarda del borrado (hoy: estado Pagado **y** fecha de pago, ver
  `isRestrictedForDelete` en `workload/columns.tsx`). El front **no debe inventar otra**: el arquitecto debe dejar esa
  condición disponible en la respuesta de la atención (por ejemplo un booleano ya calculado, `isCollected`) o documentar
  exactamente qué campos la determinan. Si el backend dice 409, manda el backend (la UI es solo presentación).
- **Solo viajan los campos que cambiaron.** `grossAmount` y `payerId` se envían únicamente si difieren del valor
  guardado. Así una edición de otro campo sobre una atención cobrada nunca dispara el 409 y se evita el efecto de
  "precio del preset" que hoy reescribe `gross` al abrir. Los builders de `request-bodies.ts` suman `grossAmount`
  (número finito) y `payerId` (UUID o ausente) a `ACTIVITY_UPDATE_FIELDS` y el fixture de contrato.
- **Monto en edición no se recalcula solo al abrir.** En modo edición el efecto de precio por preset solo corre si el
  usuario cambia actividad, tipo o medio de pago; al abrir respeta el monto guardado.
- **No se muestra un neto estimado.** Se elimina el "Nuevo Neto Estimado (70%)" del `RetroactiveModal`: el cálculo real
  lo hace el backend y una cifra inventada confunde.
- **Regla de los 30 días (solo `RetroactiveModal`):** no figura en la spec ni existe en el backend y contradice la
  decisión del usuario (editable mientras no esté cobrada). Se propone **eliminarla**; el candado pasa a ser solo
  "cobrada". Ver "Puntos a confirmar".

### 2.1 Atención no cobrada: campos habilitados y aviso de recálculo

Wireframe (`RetroactiveModal`, mismo patrón en `WorkItemForm`):

```
Editar Prestación                                   [x]
ID: ... • 05/11/2026
-------------------------------------------------------
Profesional [ Ana Pérez (deshabilitado) ]  Paciente [ ... ]

Pagador *
[ Seleccionar pagador...                         v ]

Monto bruto ($)
[ $ 12500.00 ]
  Valor guardado: $ 12.500,00

( aviso de recálculo, solo si cambió monto o pagador )
 /!\ Se recalcularán los honorarios
     Al cambiar el monto o el pagador, se recalculan los honorarios
     y la distribución con las reglas vigentes. Los ajustes manuales
     que hayas hecho en esta atención se reemplazan.
-------------------------------------------------------
                         [Cancelar] [Guardar y recalcular]
```

**Cuándo aparece el aviso**
- Solo si el monto **o** el pagador del formulario difieren de los guardados al abrir. Comparación del monto numérica
  y con tolerancia de centavos (12500 = 12500.00); comparación del pagador por id.
- Desaparece solo si el usuario vuelve a los valores originales.
- No aparece al abrir, ni por cambios en otros campos (fecha, asistencia, etc.).
- No aparece si la atención está cobrada (los campos están bloqueados).

**Texto exacto del aviso** (componente `Alert` existente, variante ámbar ya usada en el modal; icono `AlertTriangle`
con `aria-hidden`):
- Título: `Se recalcularán los honorarios`
- Cuerpo: `Al cambiar el monto o el pagador, se recalculan los honorarios y la distribución con las reglas vigentes. Los ajustes manuales que hayas hecho en esta atención se reemplazan.`

**Confirmación:** no se agrega un diálogo extra. Razones: el aviso es visible antes del botón, el botón cambia de
texto a `Guardar y recalcular` (la acción dice lo que hace, como ya hacía `Confirmar y Recalcular`) y el front no sabe
si hay ajustes manuales que perder, así que un segundo diálogo agregaría fricción sin información nueva. Si el
arquitecto expone un indicador de "esta atención tiene ajustes manuales", se puede reforzar con confirmación; hoy no
se pide.

**Botón principal**
- Sin cambios en monto/pagador: `Guardar`.
- Con cambios en monto/pagador: `Guardar y recalcular`.
- En `RetroactiveModal`, `Guardar y recalcular` solo se habilita si hay al menos un cambio (como hoy) y los datos son
  válidos (monto > 0 y finito, pagador elegido).

**Validación local (mensajes bajo el campo, `aria-invalid` y `aria-describedby`)**
- Monto vacío o no numérico: `Ingresá un monto válido.`
- Monto negativo: `El monto no puede ser negativo.`
- Más de 2 decimales: `El monto admite hasta 2 decimales.`
- Pagador sin elegir (solo si el usuario lo vació o la atención no tenía y lo está tocando): ver sección 3.
- Se mantiene el límite del backend como autoridad; estos textos son ayuda temprana.

### 2.2 Atención cobrada: campos bloqueados con explicación

```
Pagador
[ OSDE                                   ]   <- campo de solo lectura (no desplegable)
Monto bruto ($)
[ $ 12.500,00                            ]   <- solo lectura
 (candado) Esta atención ya está cobrada: el monto y el pagador no se pueden modificar.
```

**Texto exacto (visible siempre, no es tooltip):**
`Esta atención ya está cobrada: el monto y el pagador no se pueden modificar.`

Se muestra **una sola vez**, debajo de los dos campos (en `RetroactiveModal`, donde el pagador y el monto son
consecutivos; en `WorkItemForm`, bajo el campo de monto y referenciado también por el de pagador). Reemplaza al `Alert`
rojo "Edición Bloqueada" del modal actual (no se bloquea todo el formulario, solo estos dos campos): es un texto de
ayuda `text-sm` con icono `Lock` (`aria-hidden`), no un `Alert` destructivo.

**Accesibilidad de los campos bloqueados**
- Un campo con `disabled` nativo **no recibe foco** y muchos lectores de pantalla no lo anuncian ni leen su
  `aria-describedby`. Por eso:
  - **Monto:** `Input` con `readOnly` + `aria-readonly="true"` + `aria-describedby` apuntando al id del texto. Sigue
    siendo enfocable con Tab, se lee su valor y la explicación. Estilo visual de deshabilitado (`bg-muted`, texto
    atenuado) para que se vea bloqueado.
  - **Pagador:** el `Select` de Radix no admite solo lectura. Cuando está cobrada se reemplaza por un `Input`
    `readOnly` con el nombre del pagador (patrón que el modal ya usa al bloquear) con `aria-readonly="true"` y el mismo
    `aria-describedby`. Un `SelectTrigger disabled` no se usa en este estado.
  - Se acepta `aria-disabled="true"` en lugar de `aria-readonly` si el desarrollador mantiene un control propio; lo
    obligatorio es: enfocable, valor leído y descripción asociada por `aria-describedby`.
- El texto es parte del flujo del documento (no `title`, no tooltip): legible por lectores de pantalla y en táctil.
- Contraste del texto explicativo: mínimo 4.5:1 sobre el fondo del diálogo (usar el token de texto secundario de la app
  y verificarlo; si `text-muted-foreground` no llega a 4.5:1 sobre el fondo real, usar `text-foreground`). El valor
  dentro del campo bloqueado también debe cumplir 4.5:1 (no usar `opacity-50` sobre el texto).
- El `BadgeLock` con tooltip del modal actual se elimina o se conserva solo como refuerzo decorativo; la información
  no depende de él.

### 2.3 Estados del formulario de edición

| Estado | Comportamiento |
|---|---|
| Cargando datos del formulario | Opciones de pagador cargándose: el select muestra `Cargando pagadores…` y está deshabilitado (`aria-busy="true"`); el botón de guardar queda deshabilitado hasta tener la lista. |
| Lista de pagadores vacía | Select con texto `No hay pagadores disponibles` y ayuda `Creá un pagador en Configuración para poder asignarlo.` No bloquea guardar otros campos. |
| Pagador/monto habilitados | Ver 2.1. |
| Pagador/monto bloqueados (cobrada) | Ver 2.2. |
| Guardando | Botón con spinner y texto `Guardando…`, deshabilitado; Cancelar deshabilitado; el diálogo no se cierra con Esc ni clic afuera mientras guarda; `aria-busy` en el diálogo. |
| Éxito | Se cierra el diálogo; toast (sonner) `Atención actualizada.` o `Atención actualizada. Se recalcularon los honorarios.`; datos refrescados. |
| Error genérico | Diálogo abierto, `Alert` destructivo inline con `errorMessageOf(e, 'No pudimos guardar los cambios. Probá de nuevo.')` y los datos del usuario intactos. Un 403 ya lo avisa el toast de acceso (`isHandledApiError`): no se duplica. |
| Error 409 (cobrada) | Ver sección 4. |
| Error 404 pagador | Mensaje genérico de 404: `No encontramos el registro. Puede que se haya eliminado.` Para el pagador, el front agrega (si el error vino al editar el pagador) `Elegí otro pagador.` en el alert. |
| Sin permiso | Sin cambio: el front solo presenta, el backend responde 403. |

El `toast.success('Actualizado correctamente')` actual de `columns.tsx` se reemplaza por los textos de arriba y **solo
se muestra tras la respuesta exitosa** (nunca cuando el cambio no se persistió).

## 3. Pagador faltante

**Qué se muestra (listas, detalle, modal):** no `—` como valor. Texto `Sin pagador` en `text-muted-foreground`
(cursiva opcional como el `italic` de "No encontrado."). En tablas de datos (`columns.tsx`, `data-schema.ts`) el mapeo
deja de convertir el faltante en `'—'`: el modelo conserva `payerName: null` y `payerId: null`, y la presentación
decide el texto `Sin pagador`. Un `—` sigue siendo válido para celdas numéricas vacías, no para el pagador.
Lectores de pantalla: la celda dice "Sin pagador" (texto real, no solo un guion).

**Select de pagador en edición**
- Si la atención tiene pagador: valor = id del pagador.
- Si **no** tiene: el `Select` queda **sin valor** (`value` indefinido/vacío) y muestra el placeholder
  `Seleccionar pagador…` (`SelectValue placeholder`). No existe una opción "Sin pagador" ni "—" seleccionable.
- **Nunca se envía** un valor falso: ni `'—'`, ni `'Unknown'`, ni `''`, ni el nombre. Si el usuario no toca el select,
  `payerId` **no viaja**. Si elige un pagador, viaja su id (UUID). El backend decide cómo trata `null`.
- Una vez elegido un pagador no hay forma de volver al "vacío" desde la UI (no se ofrece "quitar pagador": está fuera
  de la spec). Si la atención ya tenía pagador no puede quedar vacía.
- `RetroactiveModal`: las opciones fijas OSDE / Swiss Medical / Particular se reemplazan por los pagadores reales de la
  organización (`getPayers`), con `value` = id y etiqueta = nombre.
- `WorkItemForm` (modo profesional): al editar, `isPrivate` se deriva del dato guardado (pagador "Particular" =>
  marcado; pagador real => desmarcado con el select mostrando ese pagador; **sin pagador => ninguno de los dos
  estados asumidos**: casilla "Paciente Particular" desmarcada y select con el placeholder). No se debe arrancar en
  `isPrivate = true` por defecto en edición: eso es lo que hoy produce el valor falso.
- Un pagador guardado que ya no está en la lista (borrado o de otra organización) se muestra como opción
  deshabilitada con su nombre si el backend lo devuelve, para no dejar el select en blanco sin explicación.

**Dependencia con el arquitecto:** hay que definir si "Particular" se representa con `payerId = null` (como hoy envía
`WorkItemForm`: `payerId: formData.payer === PAYER_PARTICULAR ? null : formData.payer`). Si es así, **"sin pagador" y
"Particular" son indistinguibles en el dato** y la UX no puede mostrar "Sin pagador"; en ese caso el texto sería
`Particular`. Ver "Puntos a confirmar" 1.

## 4. Error 409 al editar monto o pagador de una atención cobrada mientras tanto

Escenario: el usuario abrió la edición cuando la atención estaba pendiente; otra persona (o el mismo usuario en otra
pestaña) la cobró; al guardar, el backend responde 409 con `code` propio (sugerido `activity-already-collected`).

**Mensaje exacto (lo manda el backend; este es el texto que debe tener, y es la clave de respaldo del front):**
`Esta atención se cobró mientras la editabas. El monto y el pagador ya no se pueden modificar y no se guardó ningún cambio.`

**Comportamiento del formulario**
1. El diálogo **no se cierra**.
2. Se muestra un `Alert` destructivo inline (role `alert`, el foco pasa al alert o a su título) con el mensaje. No se
   usa solo toast: el toast desaparece y el usuario perdería la explicación.
3. Se llama `router.refresh()` (y en tablas con recarga propia, `setRefreshKey`/`loadData`) para traer el estado real.
4. Al llegar la atención actualizada, el formulario entra en el estado de **atención cobrada** (2.2): monto y pagador
   vuelven a los valores guardados y quedan bloqueados con su texto explicativo; el aviso de recálculo desaparece.
5. Los **demás campos que el usuario editó se conservan** (el efecto de inicialización del formulario debe depender de
   la identidad de la atención —su `id`— y no reinicializarse al cambiar el objeto refrescado). Si por razones técnicas
   no se pudiera, el alert debe decirlo; hoy se pide conservarlos.
6. El botón principal vuelve a `Guardar` y se puede reintentar para los demás campos (que seguirán funcionando).
7. Si el 409 se debe a otro motivo (otro `code` de conflicto), se muestra el mensaje del backend sin refrescar
   automáticamente.

Para decidir el comportamiento el front compara el `code` (`API_ERROR_CODE.ACTIVITY_ALREADY_COLLECTED`, nombre final
del arquitecto), no el texto.

## 5. Error 409 al borrar un pagador con reglas de honorarios

### Situación real
Hoy **no hay UI para borrar un pagador** (no existe `deletePayer` ni botón en `PayerRulesManager`). La spec dice "la UI
muestra el mensaje" (criterio 11): para cumplirlo hace falta una acción de borrado. Se propone el mínimo, reutilizando
componentes existentes, y se lo marca como punto a confirmar por el PO (ver abajo). Si el PO decide no agregarlo, esta
sección queda sin aplicar y el 409 solo lo ve un cliente de la API; el tester lo verifica a nivel API.

### Diseño mínimo (si se aprueba)
- En cada tarjeta de pagador propio de `PayerRulesManager` (solo los editables, no "Particular" ni los de organización)
  un botón icono `Eliminar pagador` (`Trash2`, `variant="ghost"`, `aria-label="Eliminar pagador {nombre}"`, mismo estilo
  que el botón `Confirmar cambio` de la tarjeta).
- Abre `ConfirmDialog` existente, `variant="destructive"`.

**Diálogo de confirmación (el front ya tiene la info, sin endpoints nuevos).** `PayerRulesManager` ya carga
`getFeeRules()`; un pagador tiene reglas si existe alguna con `rule.payerId === payer.id`. Entonces:

- **Pagador sin reglas en la lista de reglas cargada:**
  - Título: `Eliminar pagador {nombre}`
  - Descripción: `¿Estás seguro de que querés eliminar este pagador? Esta acción no se puede deshacer.`
  - Botón: `Eliminar`.
- **Pagador con reglas (detectado en el cliente):** no se abre la confirmación destructiva; el botón sigue habilitado
  (para poder explicar) y abre el mismo diálogo en modo informativo:
  - Título: `No se puede eliminar {nombre}`
  - Descripción: `Este pagador tiene reglas de honorarios asociadas. Para eliminarlo, primero tenés que quitar esas reglas.`
  - Solo botón `Entendido` (sin acción destructiva).
  Esto es una ayuda de cortesía: **el backend sigue siendo la autoridad** (la lista cargada puede estar desactualizada o
  paginada). Nota: hoy la pantalla no tiene forma de quitar una regla; el texto "quitar esas reglas" puede dejar al
  usuario sin salida. Alternativa que no promete nada: `Este pagador tiene reglas de honorarios asociadas y no se puede eliminar.`
  Se recomienda esta versión sin instrucción, mientras no exista una acción para quitar reglas.
  **Texto definitivo:** `Este pagador tiene reglas de honorarios asociadas y no se puede eliminar.`

**Error 409 del backend (la lista estaba desactualizada o no se detectó):**
- Mensaje exacto (viene del backend; clave de respaldo en la sección 7):
  `No se puede eliminar el pagador porque tiene reglas de honorarios asociadas.`
- Se muestra como **toast de error** (`toast.error(errorMessageOf(e, ...))`), consistente con el borrado de staff y de
  atenciones. El pagador queda en la lista, sin cambios. Como `ConfirmDialog` se cierra solo al confirmar, el toast es
  el único canal: debe permanecer visible el tiempo habitual de sonner y ser leído por lectores de pantalla (sonner usa
  `aria-live`).
- Tras el 409, refrescar la lista (`fetchData()`) para que la detección del cliente quede al día.

### Otros estados del borrado de pagador
- Éxito: toast `Pagador eliminado`, la tarjeta desaparece, foco al botón `Agregar Pagador` (o a la tarjeta siguiente).
- Pagador con atenciones: lo informa el arquitecto (spec). Si cambiara el comportamiento se consulta; la UX no agrega
  texto hasta entonces.
- Error 404: `No encontramos el registro. Puede que se haya eliminado.` + refrescar la lista.
- Error 5xx / red: `Ocurrió un problema de nuestro lado. Probá de nuevo en unos minutos.` (ya existe).
- Cargando: el botón de la tarjeta se deshabilita mientras se borra (`aria-busy`).

## 6. Borrado de staff que pasa a baja lógica

**Qué cambia visible:** nada para el usuario. La spec lo pide ("no cambia la experiencia"). El `ConfirmDialog`, el texto
y el toast `Profesional eliminado` se mantienen. No se distingue entre borrado físico y baja lógica en la UI: ambos
significan "ya no aparece en la lista de profesionales".

**Ajuste de texto de confirmación (opcional, recomendado):** el texto actual dice `Esta acción no se puede deshacer.`
Sigue siendo cierto desde el punto de vista del usuario (no hay "restaurar" en la UI); se mantiene sin cambios.

**Historial:** el nombre del staff dado de baja **debe seguir visible** en las atenciones donde participó y en las
distribuciones (tablas de atenciones, detalle de atención, liquidaciones). Requisito para el backend/arquitecto: las
consultas que devuelven participantes y beneficiarios incluyen las filas con `deletedAt` (hoy el front toma el nombre
de la respuesta). Para la UI:
- No se agrega ningún sufijo ni insignia obligatoria. Opcionalmente, en detalle de atención se puede mostrar
  `(ya no está en la organización)` en `text-muted-foreground`; **no es requisito** de esta feature.
- La lista `Gestión de Profesionales` y los selects de carga de atenciones nuevas no ofrecen al staff dado de baja.
- En la **edición** de una atención con un participante dado de baja, el select de ese rol debe mostrar su nombre (no
  quedar en blanco): se incluye como opción deshabilitada si el backend lo devuelve.

**Errores:** si aparece un vínculo entre la verificación y el borrado y el backend responde 409 (alternativa del
criterio 12), el mensaje viene del backend y se muestra con `toast.error(errorMessageOf(...))` como hoy. Sugerido para
el backend: `No se pudo eliminar al profesional porque cambió mientras lo eliminabas. Probá de nuevo.` (ver sección 7).
Nunca el 500 genérico. Estados: cargando (el diálogo cierra y la lista muestra `Cargando profesionales...` al
recargar, como hoy), éxito (toast + lista actualizada), error (toast).

## 7. Textos nuevos para `API_ERROR_MESSAGES` (claves sugeridas)

## 8. Teclado, foco y lectores de pantalla

- **Orden de tabulación del diálogo:** campos en orden visual; en el bloque de monto/pagador, aviso de recálculo
  (no enfocable, solo lectura) o texto de bloqueo (leído vía `aria-describedby`), luego Cancelar y el botón principal.
- **Foco inicial:** al abrir, el primer campo editable (Radix `Dialog` ya hace trap y devuelve el foco al disparador al
  cerrar). En atención cobrada el primer campo enfocable puede ser el monto de solo lectura (se lee con su explicación).
- **Aviso de recálculo:** región `role="status"` / `aria-live="polite"` presente en el DOM; al aparecer se anuncia sin
  quitar el foco del campo que el usuario está editando. No debe robar el foco.
- **Error de guardado (incluye 409):** `Alert` con `role="alert"`; al producirse el error el foco se mueve al alert
  (`tabIndex={-1}`), y desde ahí Tab continúa a los campos. En el 409 el mensaje queda visible hasta que el usuario lo
  cierre o guarde de nuevo.
- **Guardando:** botón con `aria-busy="true"` y `disabled`; el cambio de texto a `Guardando…` se anuncia por una región
  `aria-live="polite"`.
- **Esc** cierra el diálogo salvo mientras se guarda. **Enter** en un campo de texto/monto equivale a pulsar el botón
  principal solo si está habilitado.
- **Campos obligatorios y errores:** `aria-required="true"` en monto y pagador cuando están editables;
  `aria-invalid="true"` + `aria-describedby` al mensaje de error de validación cuando falla.
- **Etiquetas:** cada control con `<label htmlFor>` real (los `Label` actuales del modal no tienen `htmlFor`/`id`:
  corregirlo en los dos campos que toca esta feature). Los iconos (`Lock`, `AlertTriangle`, `Trash2`) con
  `aria-hidden` salvo el botón icono, que lleva `aria-label`.
- **Contraste (WCAG 2.1 AA, 1.4.3 y 1.4.11):** texto ≥ 4.5:1; bordes de campos y estados de foco ≥ 3:1. El alert
  ámbar existente usa `text-amber-900` sobre `bg-amber-50` (cumple); el alert destructivo, `text-red-900` sobre
  `bg-red-50` (cumple). No comunicar el estado solo por color: el aviso tiene título y texto; el bloqueo tiene texto e
  icono.
- **Foco visible** (2.4.7): se conserva el anillo de foco de los componentes shadcn; no se lo quita en los campos de
  solo lectura.
- **Botón de eliminar pagador:** `aria-label` con el nombre; el `ConfirmDialog` devuelve el foco al botón que lo abrió
  (si la tarjeta se borró, al botón `Agregar Pagador`).

- Diálogos: `sm:max-w-[500px]`/`520px` y `max-h-[90vh] overflow-y-auto` existentes. En móvil (< 640 px) el diálogo

## 10. Criterios de UX verificables (para el tester)

1. Atención **no cobrada**: en `RetroactiveModal` y en `WorkItemForm` en edición, el monto y el pagador se pueden
   editar.
2. Al abrir la edición **no** aparece el aviso de recálculo. Cambiar solo la fecha o la asistencia **no** lo muestra.
3. Al cambiar el monto **o** el pagador aparece el aviso con exactamente: título `Se recalcularán los honorarios` y
   cuerpo `Al cambiar el monto o el pagador, se recalculan los honorarios y la distribución con las reglas vigentes. Los ajustes manuales que hayas hecho en esta atención se reemplazan.`
   Si el usuario vuelve a los valores originales, el aviso desaparece.
4. Con el aviso visible el botón dice `Guardar y recalcular`; sin él, `Guardar`.
5. No existe el texto "Nuevo Neto Estimado" ni la cifra del 70 % en el modal.
6. Guardar con éxito (monto o pagador) cierra el diálogo, muestra el toast de éxito **después** de la respuesta del
   backend y la tabla muestra el monto/pagador nuevos (tras el refresco). Nunca hay toast de éxito si el backend
   rechazó el cambio.
7. Atención **cobrada**: monto y pagador no se pueden modificar; se ve, sin pasar el mouse, el texto exacto
   `Esta atención ya está cobrada: el monto y el pagador no se pueden modificar.`
8. En atención cobrada, con Tab se llega al monto y al pagador (solo lectura), el lector de pantalla lee valor y texto
   explicativo (`aria-describedby` presente y apuntando a un id existente); los campos tienen `aria-readonly="true"`
   (o `aria-disabled="true"`); contraste del texto ≥ 4.5:1.
9. En atención cobrada, editar solo otros campos funciona y el pedido **no** incluye `grossAmount` ni `payerId`.
10. En edición de una atención con preset y monto guardado, el monto mostrado al abrir es el guardado (no el del
    preset) y no se envía si no se tocó.
11. Atención sin pagador: la lista y el modal muestran `Sin pagador` (no `—`); el select muestra el placeholder
    `Seleccionar pagador…`; guardar sin tocar el pagador no envía `payerId` (en ningún caso se envía `'—'`, `'Unknown'`
    ni `''`); elegir uno envía su id.
12. `RetroactiveModal` lista los pagadores reales de la organización (no OSDE/Swiss Medical/Particular fijos) y manda
    ids.
13. 409 por cobro simultáneo: el diálogo sigue abierto, el alert muestra exactamente
    `Esta atención se cobró mientras la editabas. El monto y el pagador ya no se pueden modificar y no se guardó ningún cambio.`,
    se ejecuta el refresco de datos, monto y pagador quedan bloqueados con su texto, y los demás campos editados se
    conservan.
14. Borrar un pagador con reglas (si se agrega la acción): el diálogo informa que no se puede eliminar; si el backend
    responde 409, el toast muestra exactamente
    `No se puede eliminar el pagador porque tiene reglas de honorarios asociadas.` y el pagador sigue en la lista. Un
    pagador sin reglas se elimina con toast `Pagador eliminado`.
15. Borrar un profesional con vínculos: el usuario ve el mismo diálogo y toast `Profesional eliminado`, desaparece de
    la lista de profesionales y su nombre sigue viéndose en las atenciones históricas donde participó. Nunca se
    muestra el error genérico de servidor.
16. Ningún mensaje de error muestra JSON, `code` ni texto crudo de la respuesta.
17. Estados: mientras se guarda, el botón está deshabilitado con `Guardando…`; el diálogo no se cierra con Esc ni clic
    afuera; en error, los datos del usuario no se pierden.
18. Responsive: a 360 px de ancho no hay scroll horizontal, los textos de aviso y bloqueo son legibles completos y los
    botones del footer son accionables.

## 11. Puntos a confirmar / observaciones sobre la spec

La spec alcanza para diseñar; no hay bloqueo. Estas son observaciones para PO y arquitecto:

1. **"Sin pagador" vs "Particular".** El front envía `payerId: null` para Particular. Si el backend también guarda
   `null` cuando falta el pagador, ambos casos son indistinguibles y el texto "Sin pagador" no aplica. El arquitecto
   debe indicar cómo se distingue (por ejemplo, Particular como pagador con id). Hasta entonces el diseño supone que
   "faltante" es un caso distinto.
2. **Definición de "cobrada" visible para el front.** Debe llegar en la respuesta de la atención (booleano ya resuelto,
   o los campos exactos). El front hoy usa `status === PAID` para algunas decisiones y `PAID && paymentDate` para el
   borrado; deben unificarse con la definición del backend.
3. **Regla de 30 días del `RetroactiveModal`.** Contradice la decisión del usuario (editable mientras no esté cobrada) y
   no existe en el backend. Se propone eliminarla; confirmar con el PO.
4. **No hay UI de borrado de pagador.** El criterio 11 ("la UI muestra el mensaje") exige agregar un botón mínimo en
   `PayerRulesManager` (sección 5). Confirmar con el PO si entra en 017; si no, el criterio de UI se cubre solo a nivel API.
5. **"Quitar reglas" no existe en la UI.** Un pagador con reglas no puede borrarse y la UI no ofrece cómo quitarlas.
   Es una limitación visible: el texto no promete una solución. No se pide resolverla acá (fuera de alcance).
6. **Forma única de `splits` (#40).** `PayerRulesManager` lee `splits[].role/percentage` y escribe
   `{ role, percentage, beneficiaryType }`. Si el backend pasa a `{beneficiary, type, value}`, esa pantalla debe seguir
   mostrando y guardando el mismo porcentaje; el usuario no debe notar cambios. Es el único ajuste de esa pantalla
   que cubre la spec.
7. **Edición en `WorkItemForm` reinicia participantes** (`participantsByRole: {}` al abrir). Si el recálculo del backend
   reemplaza participantes, el formulario no debe mandar participantes vacíos ni inventados; fuera de alcance de este
   documento, pero conviene que el arquitecto lo revise.
8. **Ajustes manuales.** El front no sabe si existen; el aviso es siempre el mismo. Si el arquitecto expone el dato, se
   puede mostrar el aviso solo cuando corresponda.
